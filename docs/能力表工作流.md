# 能力表工作流

> 给以后改这个项目的人 / AI：**加了用户能感知的新功能，就登记能力表**。
> 这不是可选步骤——能力表是她“知道自己会什么”的唯一来源，漏了/写错了，
> 她就会在聊天里吹牛或装不会。

相关文件：

| 文件 | 作用 |
|---|---|
| [`qqbot/capabilities.py`](../qqbot/capabilities.py) | 能力表定义 + 手写条目 `MANUAL_CAPABILITIES` |
| [`qqbot/capabilities_auto.json`](../qqbot/capabilities_auto.json) | commit trailer 自动登记的条目，**别手改** |
| `docs/能力表.md` | 生成的人类可读版，**别手改** |
| `tools/capability_sync.py` | 读 trailer、校验、写自动条目、重生成文档 |
| `tools/check_capabilities.py` | 校验表 / 开关字段 / 指令说法 / 文档是否一致 |
| `tools/install_git_hooks.py` | 安装 pre-commit 校验 |

---

## 什么时候要登记

**要登记**：用户能感知的新功能。比如「能读合并转发了」「能查好感度了」
「上线会打招呼了」。

**不要登记**：

- 内部重构、性能优化、日志/测试改动；
- `persona.md` 的人设修改（称呼、关系、真名、性格）——这些留在 persona，
  进了能力表她就会照着说出来，出戏；
- 纯 `.env` 默认值调整（除非它让某个能力第一次真正可用）。

判断标准：**“群友/主人能不能在聊天里感觉到她会了一件新事？”** 能，就登记。

### 能力 = 她会说 + 她会调

登记一条能力时多问一句：**换一种说法，她还能不能做到？**
只靠本地整句指令通常不行——那就必须同时给模型一个能自己调的工具，
格式和写法见 [工具规范.md](工具规范.md)，收尾跑 `python tools/check_tools.py`。
只写指令、不写工具，她会嘴上答应、实际没做（2026-10-30 直播换台实锤）。

---

## 推荐方式：commit trailer

在 commit message 末尾写：

```text
feat: 合并转发支持引用里的记录

Capability: 别人转发的聊天记录，你能读到里面的话
Capability-Key: forward
Capability-Flag: enable_forward
Capability-Label: 合并转发
Capability-Short: 转发
Capability-Off: 关闭合并转发
Capability-On: 打开合并转发
Capability-Note: 要不要读别人转发的聊天记录
```

字段：

| trailer | 必填 | 说明 |
|---|---|---|
| `Capability` | 是 | 她自己的口吻，一句话，≤50 字；不要写代码名 |
| `Capability-Key` | 是 | 唯一 key；可聊天开关的用 prefs 里的 key |
| `Capability-Label` | 是 | 中文名，≤20 字 |
| `Capability-Flag` | 否 | `Config` 里的字段名；没有开关就不写 |
| `Capability-Off` / `On` | 否 | 必须成对；必须能被 `commands.parse()` 认出来 |
| `Capability-Short` | 否 | 「状态」里的短名，≤12 字；默认用 Label |
| `Capability-Since` | 否 | 默认用提交日期；格式 `YYYY-MM-DD` |
| `Capability-Note` | 否 | 「指令」清单里的备注 |
| `Capability-Audience` | 否 | `all`（默认）/ `owner` |

支持一个提交写多条 `Capability:`。

然后：

```powershell
python tools/capability_sync.py            # dry-run：先看会加什么
python tools/capability_sync.py --apply    # 校验 → 写 capabilities_auto.json → 重生成 docs/能力表.md
python tools/capability_sync.py --apply --test  # 再跑行为测试
```

脚本会拒绝：重复 key、不存在的 Config 字段、`Off`/`On` 和 key 对不上、
缺 Key/Label、未来日期、把人设词写进能力。

## 手写方式（少用）

需要反复斟酌措辞、或者要改老条目时，直接改
[`qqbot/capabilities.py`](../qqbot/capabilities.py) 的 `MANUAL_CAPABILITIES`：

```python
Capability(
    key="xxx",
    skill="一句话说她会做什么，用她自己的口吻",
    since="2026-10-26",
    flag="enable_xxx",       # 没有开关就删掉
    label="中文名",
    off="关闭xxx",            # 只有能聊天开关时才写
    on="打开xxx",
    note="备注",
),
```

`capabilities_auto.json` 不要手改；要改自动条目，改 commit trailer 或手动搬进
`MANUAL_CAPABILITIES`。

## 收尾检查

```powershell
python tools/check_capabilities.py --write   # 校验 + 重生成 docs/能力表.md
python tools/test_capability_table.py        # 她真的会按开关改口吗
python tools/test_capability_sync.py         # trailer 解析 / 校验
python tools/check_command_spec.py           # 指令文档 vs 代码
python tools/check_tools.py                  # 新功能对应的工具格式合规
```

然后**重启机器人**。`_system_prompt` 在启动时把「最近学会」定下来，
不重启她不知道新的一条。

## pre-commit（可选，但推荐）

```powershell
python tools/install_git_hooks.py
```

装完每次 `git commit` 前自动跑 `check_capabilities` + `check_command_spec`，
不过就不让提交。卸载：

```powershell
python tools/install_git_hooks.py --uninstall
```

> **沙箱注意**：这个 agent 的 Windows 沙箱里 Git 的 `sh.exe` 起不来
> （`couldn't create signal pipe`），装 pre-commit 会让所有提交失败。
> 在普通 PowerShell 里装；如果只能在沙箱里提交，用 `git commit --no-verify`，
> 但先手动跑上面两条检查。

---

## 不要做的事

- 不要手改 `docs/能力表.md`（它是生成物）；
- 不要把 `persona.md` 的修改搬进能力表；
- 不要把 commit 标题直接当 `Capability:`（开发者黑话，会污染她的人设）；
- 不要为了“显得功能多”把内部开关（`enable_semantic`、`enable_search_gate` 之类）
  写进能力表，除非用户真的能感知。
