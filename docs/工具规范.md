# 工具规范

> 给以后加功能的人 / AI：**用户能感知、需要她动手或去查的功能，除了本地指令，
> 还要给模型一个 she 自己能调的工具（function calling）**。
> 只写指令不写工具，遇到正则没覆盖的说法，她就会嘴上答应、实际没做
> ——2026-10-30 00:54「进入asaki的直播陪看」就是这么翻车的。

相关文件：

| 文件 | 作用 |
|---|---|
| [`qqbot/tool_spec.py`](../qqbot/tool_spec.py) | `make_tool()` 造 schema + 校验器 |
| `tools/check_tools.py` | 跑一遍所有工具：格式、命名、参数、重名 |
| [`qqbot/live_tools.py`](../qqbot/live_tools.py) | 参考实现：4 个工具，读写权限分开 |
| [`qqbot/group_tools.py`](../qqbot/group_tools.py) | 参考实现：退群（不可逆写操作，只有主人能用） |
| [`qqbot/llm.py`](../qqbot/llm.py) | provider 挂载 + 运行时格式自检 |

---

## 1. 什么时候必须有工具

**要有**：用户在聊天里说一句，她需要「真的去做点什么」或「去查点什么」。

- 改设置、开关功能、换直播房间、停直播；
- 查状态/余额/账本/开播状态；
- 抓画面、发截图、搜视频、记东西；
- 任何会改变外部状态或产生费用的动作。

**可以没有**：

- 纯被动行为（上线问候、自动复读、跟着接话）；
- 已经有自动路径、不需要模型决定的行为（例如问画面时自动从缓冲挂图 + 发截图）；
  但要在能力表/文档里写清「这是自动的」，别让下一个改的人以为漏了工具；
- 只由本地指令触发的管理操作（但也建议给工具，见下）；
- 完全不需要模型判断的内部逻辑。

判断标准：**群友/主人换一种说法，她还能不能做对？** 只靠正则，答案通常是「不能」。

## 2. 格式：一律用 `make_tool()`

```python
from .tool_spec import make_tool

def schemas(self) -> list[dict]:
    return [
        make_tool(
            "bili_live_watch",                       # 名字
            "开始盯/切换一个 B 站直播间……只有主人能用。",  # 描述
            {                                        # 参数（可空）
                "target": {
                    "type": "string",
                    "description": "房间号、直播间链接或 UP 主名字",
                }
            },
            ["target"],                              # required（可空）
        ),
    ]
```

不要手写 schema 字典：手写容易漏 `required`、参数没描述、名字大小写不一致
（`check_tools` 会抓，但一开始就用对的更省事）。

### 名字

- `^[a-z][a-z0-9_]{2,47}$`，全机器人唯一；
- 建议 `<域>_<动作>`：`bili_live_watch`、`today_spend`、`set_signature`；
- 不写中文、不写大写、不写连字符。

### 描述（最重要）

12~600 字（唯一的例外见 §6），必须写清四件事：

1. **什么时候用**：把用户可能的说法写进去（「主人说『看直播』『进入某人的直播陪看』时用」）；
2. **做什么**：会不会真的改状态、会不会发东西；
3. **返回什么**：成功/失败分别是什么样；
4. **权限/副作用**：只有主人能用、会发图、会写库、会花钱。

反例：

```text
"查直播"                       # 太短，模型不知道什么时候调
"看看画面"                     # 没说会不会发图、没在播怎么办
"主人说看直播时用"              # 没写返回什么、没写权限
```

### 参数

- 必须是 `{"type": "object", "properties": {...}}`；
- 每个属性都要 `type` + `description`；没有参数就空 properties；
- `required` 里只能是 properties 里有的名字；
- 参数名小写 snake_case，可以短（`to` / `up` / `x`）；
- 有枚举就写 `enum`，别让模型自由发挥。

### 返回

- 中文，尽量 ≤400 字；
- 失败说实话：「现在没在播，发不了截图」，不要编成功；
- 不要返回 Markdown 链接（QQ 会拦），要提链接就说域名；
- 不要把内部异常栈、文件路径甩给模型。

### 权限

- 写操作（改设置、换房间、停直播、删人、发图）：**schema 暴露**和 `run()`
  里**双重把关**，只有主人能用；群友的只读查询单独开放；
- 只读查询（状态、弹幕、余额）：可以开放给群友；
- 在 `run()` 里挡的时候要返回一句人话，别返回 `None` 让模型以为工具不存在。

参考 `live_tools.run()`：不在白名单返回 `None`（不是我的工具）；
群友调写操作返回「只有主人能……」。

---

### run() 的签名（必看，2026-11-01 栽过）

`llm.reply` 分发工具时是这么调的：

```python
provider.run(name, arguments, ori_question=..., _tool_charges=..., **ctx)
```

**所以 `run()` 必须能接住这些关键字参数**，标准写法：

```python
async def run(
    self,
    name: str,
    arguments: str = "{}",
    **kwargs: Any,
) -> str:
```

漏了 `**kwargs`，schema 校验全过、`check_tools` 也全绿，但**模型第一次调用就
TypeError**，用户收到的是「（出错了：TypeError，等会儿再试）」。

### 新入口：`turn: Turn`（2026-11-05 起，迁移中）

`llm.reply` **只传** `turn`（2026-11-05 起单轨）：

```python
provider.run(name, arguments, turn=turn)
```

`Turn`（`qqbot/turn.py`）装"这一轮是谁、在哪儿、问的什么"：`session /
speaker_uid / speaker_nick / is_owner / owner_live / now / ori_question /
catchup / task / …`，过渡期的业务引用放 `turn.services`。

**意义**：换 agent runtime（DSL、DSH 之类）只要造得出一个 `Turn`，所有工具一行不用改。
pp.py 那一万行再大，也不影响这一步 —— 这就是"逃生口"。

迁移期的写法（新 provider 照这个来）：

```python
async def run(self, name, arguments="{}", *, turn=None, **ctx):
    if turn is not None:
        ctx = turn.as_ctx()      # 老代码继续 ctx.get("xxx")，行为不变
```

`live_tools.py` 已经迁完，可以照抄。

### 通用能力走 `qqbot/caps` 端口

屏幕 / 画面 / ASR / TTS 这类**通用能力**，业务代码不许直接 `import live_frames`，
一律从 `self.capabilities`（`qqbot/caps/`）拿：

```python
shot = await self.capabilities.frames.snapshot()   # 拿不到就是 None
```

将来接 dsh-see-now 或本地 ASR 服务，只加一个实现类，业务不动。


现在 `tools/check_tools.py` 会逐个检查所有 provider 的 `run()` 签名
（`FriendQueryTools.run() 接受 **kwargs` 这类行），漏了直接 FAIL。

## 3. 注册步骤（加一个工具照这个顺序）

1. 在对应 `*_tools.py` 里加 `schemas()` 条目 + `run()` 分支（签名带 `**kwargs`）；
2. 需要新 provider 的，在 `llm.py` 的 ctx 组装处挂上（注意 owner/群聊/私聊门槛）；
   同时把它加进 `tools/check_tools.py` 的 `collect()` 和 `run_signature_classes()`；
3. 写测试（至少：schema 合规、认名字、`run()` 返回、权限拦截）；
4. 跑 `python tools/check_tools.py`；
5. 用户能感知的，按 [能力表工作流.md](能力表工作流.md) 登记能力；
6. 在 指令大全.md 补一句「也可以直接说……」的触发说法（如果适用）；
7. 收尾跑 `python tools/check_git_dirty.py`。

---

## 4. 权限门槛写在哪

| 位置 | 作用 |
|---|---|
| `llm.py` 的 `providers.append(...)` | 决定模型**看不看得到**这个工具（schema 级） |
| provider 的 `run()` | 决定**执行时**放不放行（行为级） |

两处都要有。只挡一处，要么群友能换掉主人的房间，要么模型根本不知道有这个工具。

---

## 5. 自检

```powershell
python tools/check_tools.py
```

检查：schema 结构、名字格式、描述长度、参数类型/描述/required、provider 有没有
`run()`、全机器人工具名唯一。

运行时 [`llm.py`](../qqbot/llm.py) 也会跑同一套校验，不合规只记 warning（不拦回复），
所以**收尾必须跑一次 check_tools**，别等线上 warning。

## 6. 例外：确实需要长描述的工具

目前只有 `run_local_command`（本地指令大全，约 2.3k 字）。它需要在描述里带
完整指令清单，模型才能把自然语言映射回本地指令。

例外必须在 provider 上**显式声明**：

```python
class CommandTools:
    description_limit = 2400  # 唯一一个；别的工具不许学
```

上限硬顶 4000；没声明就按默认 600 校验。不要为了让检查过而调大默认值。

## 7. 反例清单

| 反例 | 后果 |
|---|---|
| 只加指令正则、不加工具 | 换个说法就嘴上答应、实际没做 |
| 工具只在 schema 里给主人，`run()` 不挡 | 别的路径挂进来就能越权 |
| 描述只写「查一下」 | 模型不知道什么时候调、调完说什么 |
| 参数没 `description` | 模型填错、填空 |
| 返回英文/异常/URL | 群里像机器人、或被 QQ 拦 |
| 有副作用（发图/删人）不写进描述 | 模型以为只是查一下 |
| 两个工具重名 | 后挂的覆盖前面的，行为随机 |
| `run()` 没接 `**kwargs` | schema 全过，模型一调就 TypeError（2026-11-01） |
| 新 provider 忘了加进 `check_tools.collect()` | 它从来没被校验过，等于没有检查 |
